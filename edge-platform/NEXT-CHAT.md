**НОВОЕ ПОЛНОЕ ОПЕРАТОРСКОЕ ОГРАНИЧЕНИЕ (18.10.2026): запрещено восстанавливать, продолжать, воспроизводить или адаптировать старые инфраструктурные операции ВСЕГО приложения.** Не отлаживать историческую A/B, не чинить старый `/credentials recover`, не переносить legacy-пути и профили в новый код, не запускать старые `/windows /vm /production /credentials` и т. п. PR #400 закрыт без merge по этому правилу. Архив Issue #26 хранится как пассивное доказательство, не как допуск к mutation.

**Цель:** единая нативная типизированная инфраструктура Windows + VM + sing-box + Docker + Worker secrets, управляемая из ChatGPT ровно тремя операциями `host status/apply/recover`. Rust Orchestrator единственный authority решений; SYSTEM Windows Controller и root VM Agent единственные исполнители; GitHub обеспечивает Git-owned typed desired, auth, immutable release, transport; Worker — секреты. Без второго реестра, рабочих профилей, новых служб, fallback и обходных путей.

**Путь сбоя:** запросить короткую native read-only диагностику установленного owner. Если собственный ресурс sing-box действительно сломан, выбрать новый typed desired, новый resource/operation ID, новый ReleaseSet-bound bundle, новый provision secrets в Worker, native install/reinstall/replace. Перед удалением старого нужна доказанная принадлежность и bounded impact; при UNKNOWN_NO_REPLAY никакой повтор неизвестного ACK, стирание операторского доступа, чужих проектов, самовольный запуск остановленной Windows SCM, TUN, DNS/default-route изменений, Cloudflare One.

**Реальный прогресс PR #402:** операторский GitHub ingress старых `/windows /vm /production /credentials /vultr /vpc /application` удалён; `host apply/recover` больше не читают исторический Issue #26 и не делегируют в legacy workflow. Сейчас они строго **только read-only preflight** с точной machine ID, desired path, target ReleaseSet и `host_native_install_authority=NOT_YET_ACCEPTED`. Это сознательно **не install** и не полноценный recover. Для физической новой установки требуется новая SYSTEM/root owner capability и scoped fresh ReleaseSet с receipts; не пытаться использовать старый backend напрямую. При сомнении о доступном локальном owner capability запросить один адресный read-only факт у локального агента.

**Единая реализация:** один интегрированный кодовый срез закрытия legacy ingress + fresh per-resource Host lifecycle + per-host bundle + типизированных Worker secret provision + native replace/recover. Точный кандидатный CI (source, Windows, Linux/OCI, ReleaseSet) → tested merge → immutable promotion → реальная приемка не менее двух Windows и двух VM; Line1 4/4, Line2 6/6 с TLS/auth и негативными пробами. До этих фактов статус НЕ 10/10. Физические владельцы уже имеют независимую read-only диагностику; production-1 ещё UNPROVEN.

**КРИТИЧЕСКОЕ ОБЯЗАТЕЛЬНОЕ ПРАВИЛО: при самом малом сомнении или недостающем доказательстве обязательно попросить помощи существующего локального агента.** Нельзя гадать, выводить PASS по косвенным данным или гонять одинаковые проверки по кругу. Сформулировать **одну точную безопасную read-only проверку** факта: машина, owner, недостающее поле, команда, ожидаемый формат, `MUTATIONS=0`. Не действовать на неподтверждённом состоянии. Не заявлять, что из-за доступа к GitHub локальная помощь не нужна. После получения факта исправить **штатный типизированный Rust diagnostic contract**, чтобы в готовом приложении ChatGPT сам получал его без локального участия; это обязательный критерий качества, не дополнительная служба и не legacy fallback.

**Временная локальная диагностика для агента (ТОЛЬКО ЧТЕНИЕ):** один машинно-читаемый ответ `HOST_ID, OWNER_PRESENT, OWNER_VERSION/RELEASE, OS, SERVICE/CONTAINERS, SINGBOX_MODE, DNS_DEFAULT_ROUTE_HASH_OR_SUMMARY, CREDENTIAL_PHASE_WITHOUT_SECRETS, ERROR_CLASS, NEXT_ACTION`. На Windows использовать установленный `C:\sing-box\bin\edge-diagnostic.exe doctor C:\sing-box\current.pb` (после проверки наличия) и read-only SCM/адаптеров/маршрутов. На VM — существующий `sudo -n /usr/local/libexec/sing-box/edge-agent local diagnose`, если native sudoers уже это разрешает. Если owner отсутствует, сообщить `NATIVE_OWNER_MISSING` и факты OS/прав, **не ставить второй агент, не писать конфиги/секреты, не делать repair самостоятельно**. Логи санитизировать: только вывод статуса/ошибок, не пароли/ключи/токены; никаких sleeps/polling. Если команда недоступна — `UNPROVEN`, не PASS.

Никаких «потом доделаем старым способом». При невозможности безопасно продолжать указывать точный новый недостающий ресурс/поле/владельца, обновлять Issue #26 только фактами и одним следующим действием.
